--------------------------------------------------------------------------------
1. The fix
--------------------------------------------------------------------------------

One line, in the root `package.json`:

    before:  "scripts": { "prepare": "husky" }
    after:   "scripts": { "prepare": "husky || true" }

`prepare` runs on every `pnpm install`, including the api image's `prod-deps` stage
(`pnpm install --frozen-lockfile --prod --filter=@snapscale/api...`), which has just
dropped husky itself because husky is a devDependency. `husky || true` is the guard
husky's own documentation gives for non-dev installs.

`--ignore-scripts` on that stage was considered and REJECTED: the same stage runs
protobufjs's `postinstall`, which arrives with the OTLP exporter (see §2 of the
discovery run below, where that postinstall is visible immediately before the husky
failure). Suppressing all lifecycle scripts would trade one breakage for another.

3. The guard did not silently disable the hooks
--------------------------------------------------------------------------------

The obvious risk of `|| true` is that husky stops installing anywhere and nobody
notices, because failure is exactly what the guard swallows. Checked explicitly:
`core.hooksPath` was unset, then `pnpm prepare` was run, then

$ git config core.hooksPath
.husky/_

and `.husky/_/pre-commit` is present. So the commit-time gate added by 37d4ea8
still installs in a developer checkout; only the prod-deps install, where husky is
absent by design, now degrades quietly instead of exiting 1.

--------------------------------------------------------------------------------
3. Root cause
--------------------------------------------------------------------------------

The root `package.json` carries a `prepare` lifecycle script that runs husky:

    "scripts": { "prepare": "husky", ... }
    "devDependencies": { "husky": "9.1.7", "lint-staged": "15.5.2", ... }

The api image's `prod-deps` stage installs with `--prod`, which excludes
devDependencies — so `husky` is not on PATH when pnpm runs the root `prepare`
script, `sh` reports `husky: not found`, pnpm raises ELIFECYCLE, and the stage
exits 1. The api runtime image therefore cannot be produced at this commit.

Introduced by commit 37d4ea8 "chore(git): gate commits with husky and
lint-staged" (2026-08-31), which added the `prepare` script and the husky
devDependency:

    $ git log -S'"prepare"' --oneline -- package.json
    37d4ea8 chore(git): gate commits with husky and lint-staged

Why the gate never saw it: `.github/workflows/ci.yml` runs
lint → typecheck → build → test → test:coverage, plus a `docker info` probe for
Testcontainers. It never builds a container image and never runs the Playwright
journey, so a broken image is invisible to a green CI run. The evidence this
file replaced was produced at f7d061a — fourteen commits earlier and before
37d4ea8 existed — which is why the last successful image build predates the
regression.

Blast radius is the api image only. The web image builds fine (see §1): its
Dockerfile has no `--prod` install stage, because nginx serves a static bundle.
The `migrate` service targets the api Dockerfile's `build` stage, a full
(dev-inclusive) install where husky IS present, and that stage completed — it was
CANCELED only because the sibling api target failed. Note that the same `--prod`
install pattern will fail in any future service Dockerfile that copies it.

Not fixed here, and deliberately not worked around in
`docker-compose.verify.yml`: that override exists to remap ports, and teaching it
to dodge a broken image would hide the defect from the next person who runs it.
